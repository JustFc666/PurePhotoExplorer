# 代码地图：每个文件负责什么、用了什么算法

> 配套《一个照片管理器是怎么造出来的》，这份更"实用"：**想知道某个功能在哪个文件、某段代码用了什么算法，直接查表**。
>
> 行数统计的是**生产代码**（不含测试模块）。同一个文件里测试占大头的会在备注里说明。

---

## 怎么读这张表

三列：

- **文件** —— 相对路径，点进编辑器就能定位
- **负责什么** —— 一句话说清它的边界（不含的就别指望它）
- **算法 / 关键实现** —— 真正"有技术含量"的部分；没有写"——"表示这里主要是搬数据

先看第四节「算法反查表」也行：那是按算法名反查文件的索引，讲到某个算法时最好用。

## 四、算法反查表

按算法找文件，比按文件找算法快。

| 算法 / 技术 | 用在哪 | 文件 | 关键参数 |
|---|---|---|---|
| **DCT 缩放**（跳着解 JPEG） | 缩略图、预览 | `pv-decode/src/bitmap/jpeg.rs` | 1/2～1/8 缩放，内存降 64 倍 |
| **面积加权重采样 + SIMD** | 大图缩到目标尺寸 | `pv-decode/src/bitmap/resize.rs` | `fast_image_resize` 必须开 `rayon` |
| **Magic Kernel Sharp 2013** | 72～100px 头像 | `apps/desktop/src/lib/mksResample.ts` | 比双线性锐利，比 Lanczos 快 |
| **纯手写格式解析** | BMP / PSD | `bitmap/bmp.rs`、`bitmap/psd.rs` | PackBits RLE、多图层混合 |
| **两阶段管线** | RAW | `pv-decode/src/raw/` | 先扫内嵌 JPEG 预览，再按需全解码 |
| **格式歧义降级** | TIFF vs RAW | `decoder/registry.rs` | 先试 RAW，失败降级 TIFF |
| **原子写** | 所有写回 | `pv-edit/src/opstack.rs` | 内存编码 → 临时文件 → rename |
| **EXIF 内联值判定** | 改方向标记 | `pv-meta/src/exif/rewrite.rs` | `count==1` 且 `type∈{SHORT,LONG}` |
| **blake3 内容哈希** | 缩略图缓存键 | `pv-index/src/cache_key.rs` | `path‖size‖mtime_ns‖tier` |
| **LRU + 字节预算** | L1 内存缓存 | `pv-cache/src/l1.rs` | 默认 512 MB |
| **三级回退** | 取缩略图 | `pv-store/src/thumb.rs` | L1 → L2 → 现生成 |
| **三态增量 diff** | 重扫目录 | `pv-scan/src/plan.rs` | 新增 / 变化 / 消失 |
| **事件去抖聚合** | 文件监听 | `pv-scan/src/watch.rs` | 静默一段时间才投递一批 |
| **动态 SQL + 分页** | 组合查询 | `pv-index/src/repo/query.rs` | `LIMIT/OFFSET` + 单独 `count` |
| **COALESCE 兜底排序** | 默认按拍摄时间 | `repo/query.rs` | `COALESCE(taken_at, added_ts)` |
| **余弦相似度** | 打标 / 人脸比对 | `pv-ai/src/tagger.rs`、`face.rs` | 向量先归一化，点积即余弦 |
| **两阶段图聚类** | 人脸归人 | `pv-ai/src/cluster.rs` | `chinese_whispers(0.55)` → 簇心归并 `0.50` |
| **haversine + 粗筛** | 坐标 → 城市 | `pv-geo/src/lib.rs` | 6.4 万条表，先按经纬带筛再算精确距离 |
| **Argon2id + AEAD** | 加密图库 | `pv-vault/src/format.rs` | 4 KiB 明文头 + 12 B nonce + 头部 MAC |
| **规则 DSL 解析** | 智能图库 | `pv-lib/src/rule.rs` | 属性 运算符 值，AND 连接 |
| **IntersectionObserver 窗口化** | 网格预取 | `hooks/useGridWindow.ts` | 不用 `scrollTop / 行高` |
| **对数刻度** | 缩放滑块 | `components/viewer/ZoomControl.tsx` | 5%–3200% |
| **裸字节传输** | 像素回传 | `commands/pixel.rs` + `ipc/protocol.ts` | 不 base64，省 33% 体积 |

## 五、一条完整链路：点「AI 识别」会发生什么

把上面这些文件串起来看，最直观。

```
你点「AI 识别」
 └─ AiPipelineDialog.tsx —— 只负责显示两行进度
    └─ ipc/ai.ts —— 发命令（前端唯一出口）
       └─ commands/ai/jobs.rs —— 收到命令，起一个 session
          ├─ tagger_dir() —— 定位 assets/ai/tag
          ├─ Tagger::load —— 加载 165 MB 视觉塔（一次）
          ├─ pv_ai::batch::tag —— 逐张：解码 → 预处理 → 向量 → 打分
          │   └─ pv-decode —— 解码（跳着解到 1024）
          ├─ repo::tags —— 把标签写进 image_tags
          └─ 接着跑人脸
             ├─ pv_ai::face —— YuNet 检测 + SFace 特征
             ├─ pv_ai::cluster —— 两阶段聚类出人物
             └─ repo::persons —— 建人物、清孤儿

完成后：前端收到进度 → useManager 触发 reload()
```

**这条链路里能看出分层的价值**：界面对"AI 怎么跑"一无所知，它只知道"发一条命令、收一串进度"。想换模型、换阈值、换聚类算法，全在 `pv-ai` 里改完就行，前端一行不用动。

## 最后

三个可以拿来复述的观察：

1. **越靠下的层越"纯"**。`pv-core` / `pv-geo` / `pv-vault` 几乎没有 IO 副作用，所以测试最好写；越往上（命令层、视图层）越是"编排"，测试也更偏集成。
2. **最贵的逻辑往往最少代码**。`plan.rs` 只有 63 行，但它决定了"重扫一个十万张的目录要 3 秒还是 3 分钟"；`rewrite.rs` 的 `orientation_slot` 只有 14 行，判错就毁原图。
3. **算法清单其实很短**。真正称得上"算法"的不到 25 个（见第四节），剩下 6 万行的绝大部分是**把这些算法接到正确的地方**、以及**处理它们出错时的情况**。
