# 自动打标签 + 人脸识别 · 可行性研究（PurePhotoExplorer）

> 依据：《PixSeek · Windows 发布版技术路线》（2026-10-19）
> 结论日期：2026-10-20 ｜ 目标形态：**本地推理、可分发给别人、不联网**

---

## 0. 结论

**能做，且不用分发 torch。**

| 能力 | 方案 | 可行性 | 依赖 | 预估工作量 |
|---|---|---|---|---|
| 自动打标签 | CN-CLIP 零样本 + 精选中文词表 | ✅ 高（L1/L2 主题级 85–95%） | ONNX Runtime + DirectML | 5–8 天 |
| 人脸检测 | insightface `det_10g.onnx` | ✅ 高 | 同上 | 2–3 天 |
| 人脸聚类 + 命名 | 512 维 embedding + 余弦聚类 | ✅ 中高（阈值需实测调） | 同上（纯 CPU 数学） | 3–5 天 |
| 自然语言搜图 | CLIP 全库向量 + 暴力内积 | ✅ 高（已在路线里） | 同上 | 3–5 天 |

三条与路线一致的硬约束：

1. **推理后端只走 ONNX Runtime**（DirectML EP 优先，CPU EP 兜底），模型预导出 ONNX；
2. **Win10 必须自带 onnxruntime**，不能依赖 Win11 24H2+ 的 Windows ML 动态 EP；
3. **索引离线、检索在线**：打标签是后台批处理（可暂停/续跑），检索永远走索引。

## 1. 技术选型（钉死）

### 1.1 推理运行时

Rust 侧用 `ort`（onnxruntime 的 Rust 绑定，动态链接 `onnxruntime.dll`）+ `DirectML.dll`。

- ORT-DirectML 的 DLL 体积约 **50 MB**（压缩后约 18–20 MB），覆盖 AMD / NVIDIA / Intel 所有 DX12 显卡，**核显也能跑**；
- 同一份二进制在无独显机器上自动掉到 CPU EP（限 4 线程），不需要装第二套；
- ⛔ 不引 torch / CUDA / ROCm —— 那条路对分发是灾难（CUDA 版 2.5 GB+，ROCm 版只认 gfx110x）。

> ⚠️ **待验证（半天 spike）**：`ort` 2.x 的 `directml` feature 需要配套的 ORT-DML 动态库版本，
> 且 `DirectML.dll` 要随包分发。第一步只跑一个 224×224 的空模型把 EP 打通，确认版本组合，再谈模型。

### 1.2 自动标签模型

| 项 | 值 |
|---|---|
| 模型 | `OFA-Sys/chinese-clip-vit-base-patch16`（CN-CLIP，Apache-2.0，**中文原生**） |
| 视觉塔 | 导出 ONNX，fp16 约 **170 MB**（INT8 约 88 MB，精度略降） |
| 文本塔 | **只在建词表向量时跑一次**，向量随模型包一起下发（520 词 × 512 维 ≈ 1 MB） |
| 维度 | 512 |
| 输入 | 224×224 中心裁剪（非方形图会丢信息，见 §4） |

⛔ **视觉塔与文本塔必须同源**：拿 SigLIP 的视觉塔配 CLIP 的文本塔，向量空间对不上，结果全是噪声。

### 1.3 人脸模型

> ⭐ **2026-10-24 实测定版：改用 OpenCV Zoo 的 YuNet + SFace（许可干净），弃用 insightface。**
> 见 §3.0 的实测数据与 §3.5 的选型对比。

| 项 | 值 |
|---|---|
| 检测 | **`face_detection_yunet_2023mar.onnx`（MIT，228 KB，5 关键点）** —— 项目已在用 |
| 识别 | **`face_recognition_sface_2021dec.onnx`（Apache-2.0，36.9 MB，**128 维** embedding）** |
| 对齐 | `cv2.FaceRecognizerSF.alignCrop(img, yunet_row)` —— **SFace 就是吃 YuNet 的 5 点**，不用自己写仿射 |
| 阈值 | OpenCV 官方 SFace 余弦阈值 **0.363**；本机家庭图库实测 **0.40** 更合适（见 §3.0） |
| 备选 | EdgeFace（TBIOM 2024，1.24M 参数 LFW 99.57，需自转 ONNX）—— 精度更好但工程量大一档 |
| ⛔ 弃用 | insightface `det_10g` + `w600k_r50`：精度高但**模型非商业许可**，不能随产品分发 |

## 2. 自动打标签的实现路径

### 2.1 流程

```
索引里的图 → 解码(1024 长边) → EXIF 方向校正 → 224 中心裁剪 → 视觉塔 → 512 维
      ↓
512 维 × 词表矩阵(520×512)ᵀ → 余弦相似度 → 温度缩放 softmax
      ↓
取 Top-5 且相似度 ≥ 阈值(默认 0.55) → 写 tags(source='ai') + image_tags
```

### 2.2 词表（决定 80% 效果）

**定版：395 条**（20 个一级 / 76 个二级 / 325 条同义词），文件 `crates/pv-ai/vocab/zh_tags.csv`，
由 `merge_thesaurus.py` 从《照片库中文主题词表》(518 条) 优化而来。
**条数不是目标，判别力才是** —— 从 500 压到 417 靠的是合并，不是删。

**一级类目用日常词**（直接当侧栏筛选器，不用「事件与生活时刻」这种书面腔）：

### 删减（50 条，按模型能力）

| 删什么 | 条数 | 为什么 |
|---|---|---|
| 抽象情感（爱 / 幸福 / 孤独 / 怀旧…） | 15 | CLIP 会给「柔和光线 ≈ 宁静」这种伪相关分，属于 L4，结构上做不到 |

| 与已有词重复（夜景摄影 / 电竞 / 摄影 / 农业 / 表情） | 5 | 夜景＝夜景，电竞＝游戏 |
| 无视觉符号的日期类节日（重阳 / 妇女 / 劳动 / 母亲 / 父亲 / 教师节） | 6 | 靠日历比靠模型准 |

**补齐的 42 条**：证件单据 13、截图文档 8、二次元相关 11（二次元 / 日系 / 赛博朋克 / 像素风 /
小清新 / 卡通 / 漫画 / cosplay / 手办 / 高达 / 模型）、军事 4（武器 / 刀剑 / 坦克 / 军舰）、
键盘 / 显示器 / 无人机 3、奶茶 / 便当 / 机场 3。

**原表的两个高价值资产，必须用起来：**
- **同义词（215 条带同义，共 292 个词）** → prompt 集成：同一标签跑 2–3 条模板（`猫` / `一只猫` / `小猫`）取平均，
  比单条模板稳定，是最便宜的提精度手段；合并进来的旧词也在里面，等于**零成本扩容**；
- **英文对照（417 条全带）** → 将来切 OpenAI CLIP / M-CLIP 时直接用，也方便映射回
  Places365 / Open Images V7 做回归测试。

⛔ 不做细粒度（英短蓝猫、车型年份）：CLIP 结构上只有 40–60%，上线就是砸口碑。
⛔ 不做 VLM 开放生成：会编造细节（幻觉），几万张的成本也不现实。
⛔ **EXIF 已有的一律不进词表**：时间、季节、地点、机型、尺寸都能从元数据拿到（准确率 100%）。

## 3. 人脸识别的实现路径

### 3.0 ⭐ 实测结论（2026-10-24，`tools/ai/face_probe.py`，test-image 351 张）

**两档检测分辨率的对比（同一批图、同一套模型）**：

| 检测长边 | 最小脸 | 入库脸 | 脸宽 p50 | 同图负样本 p50 | 负样本 p99 | 最大簇(τ=0.363) |
|---|---|---|---|---|---|---|
| 1024 | 24 px | 367 | 43 px | 0.285 | 0.585 | **146 张脸（明显过合并）** |
| **2048** | **56 px** | **327** | **117 px** | **0.181** | 0.612 | 90 张脸 |

⭐ **1024 长边不可用**：小脸的 embedding 基本是噪声，负样本 p50 从 0.181 抬到 0.285，
表现在界面上就是"张冠李戴"。**原点图 4000px 的脸降到 1024 长边只剩 40px**。
→ 检测分辨率定 **2048 长边**，最小脸 **56px**（≈ 原图 110px）。

**阈值 0.40 + Chinese Whispers 的簇，用拼图人眼核对（`--dump` 导出）**：

| 簇 | 脸数 | 图片数 | 人工核对结果 |
|---|---|---|---|
| cluster_01 | 87 | 63 | ✅ 全部是同一个孩子（婴儿→学龄） |
| cluster_02 | 64 | 63 | ✅ 全部是同一位成年女性 |
| cluster_03 | 41 | 32 | ✅ 同一位年轻女性 |
| cluster_04 | 34 | 34 | ✅ 同一位戴眼镜成年男性 |

⭐ **结论：0.40 可用。** 负样本 p99 高达 0.612 不是模型差，而是**家人之间本来长得像**
（父子/兄弟姐妹），所以不能用"负样本分布上界"机械定阈值 —— 家庭相册必须靠人眼核对。

#### 3.0b ⛔ 混合图库（含社媒美颜图）把单阈值打穿了

图库「测试图库」= `test-image`(372) + `rednote`(373)，共 **745 张**
（737 可解码 / 566 含脸 76.8% / 737 张脸入库 / 丢小脸 478 / 合影 165）：

| 方案 | 最大簇 | 人眼核对 |
|---|---|---|
| 单阈值 **0.40** + CW | **221 张脸 / 209 图** | ❌ **过合并**：一整屏不同的童模被并成一簇 |
| **两阶段 0.55 / 0.50** | **37 张脸 / 37 图** | ✅ 干净，全是同一个女孩 |

**元凶是 `rednote` 那批小红书图**（单独跑 407 张脸）：

```
同图负样本   p50=0.258  p90=0.505  p99=0.761  max=0.828
```

**不同的人相似度能到 0.83** —— 在正常库里这是"同一人"的分数。原因是重度美颜
（磨皮/大眼/瘦脸）+ 同风格棚拍：**所有向量一起塌向"平均脸"，类内类间分布完全重叠**。
这不是调阈值能解决的，任何单一阈值在这类数据上必然二选一地崩。

⭐⭐ **定稿算法：两阶段聚类**

```
① 严阈值 CW(t_core=0.55)  → 只信高纯度"核心簇"
② 散脸按"离簇心(medoid)多远"并入，cos > t_join=0.50 才并
```

只有簇心参与二次判定，比两两比较抗噪声。实测全库 105 簇里 65 个是单例
（模特图里很多人只出现一张，正常）。

**产品口径**：
- **只给 ≥3 张脸的簇建「人物」**，单例不建（Immich 同口径）；
- 误合并比误拆分更伤（用户不易察觉）→ 阈值偏严，靠 **合并/拆分 UI** 兜底；
- 命名永远由用户给（零幻觉）。

### 3.1 流程

```
逐张图（跑已有 L2 缩略图，2048 长边） → YuNet 检测（框 + 5 关键点）
      → FaceRecognizerSF.alignCrop（SFace 直接吃 YuNet 的 5 点）
      → SFace → 128 维归一化 embedding → 量化 int8 写 faces
      → 两阶段聚类（0.55 出核心簇 → 0.50 按簇心并入）
      → 只给 ≥3 张脸的簇建 persons（未命名 ①②）→ 用户命名
```

### 3.2 表设计

> ⚠️ `pv-index/schema.rs` 里现成的 `faces` / `persons` 是**预留空壳**，要用得改 5 处（2026-10-24 定）：
> ① 坐标从 INTEGER 像素改**归一化 REAL**（缩略图档位会变，像素坐标会失效）+ 记 `tier`；
> ② 加 `model TEXT`（**换模型必须整库重建**，向量空间不同不能混）；
> ③ `embedding` 存 **int8 量化**（128 维 × 1B = 128B/脸；f32 是 512B）；
> ④ 加 `score` / `quality`（小脸、模糊脸的向量不可信，聚类前先过滤）；
> ⑤ `persons` 加 `face_count` / `cluster_version`。
> ⛔ **不存人脸图片**：用 x,y,w,h 从已有 L2 缩略图裁，缓存是现成的。

```sql
CREATE TABLE faces (
  id        INTEGER PRIMARY KEY,
  image_id  INTEGER NOT NULL REFERENCES images(id),
  person_id INTEGER REFERENCES persons(id),
  x REAL, y REAL, w REAL, h REAL,     -- 归一化坐标（相对检测用的那一档）
  tier      INTEGER,                  -- 在哪一档缩略图上量的
  model     TEXT,                     -- 模型版本（sface_2021dec）
  score     REAL, quality REAL,       -- 检测分 / 质量（脸宽像素）
  embedding BLOB                      -- 128 × int8（已归一化）
);
CREATE INDEX idx_faces_person ON faces(person_id);

CREATE TABLE persons (
  id INTEGER PRIMARY KEY,
  name TEXT,                          -- 用户给的名字；未命名就是 NULL（零幻觉）
  cover_face_id INTEGER,
  face_count INTEGER,
  cluster_version TEXT,
  created_ts INTEGER
);
```

**落地状态（2026-10-24）**：`pv-index` schema 已升到 **v4**（`DDL_V4`，DROP 重建这两张空壳表），
仓储已就位：

| 模块 | 提供什么 |
|---|---|
| `repo::faces` | `replace_for_image`（按图幂等重写）、`list_by_image`、`list_by_person`、`list_unassigned`（含小脸过滤）、`set_person`、`delete_all`、`quantize/dequantize/cosine` |
| `repo::persons` | `insert`、`list(min_faces)`（命名优先）、`rename`、`merge`、`split`、`delete`（只解绑不删脸）、`refresh_count/refresh_all` |

护栏测试：int8 量化往返误差 <1%、按图重写幂等且刷新内容、大脸自动当封面、
小脸不进聚类池、合并到不存在的人物要报错、拆分不留空壳、删人物不删脸。

### 3.3 聚类与命名（关键：模型只归堆，名字用户给）

- **算法**：Chinese Whispers **两阶段**（`t_core=0.55` 出核心簇 → `t_join=0.50` 按簇心并入）。
  ⛔ 不要退回单阈值：实测混合图库上单阈值 0.40 就把 221 张脸糊成一团。
  ⛔ 不要用「负样本分布上界」机械定阈值 —— 家人/美颜图会让它失真，必须靠拼图人眼核对。
- **建人物的门槛**：只给 **≥3 张脸**的簇建 `persons`，单例只保留 `faces` 行（不占侧栏）。
- **零幻觉**：未命名就是「未命名 ①」，绝不猜「这是张三」。
- 纠正闭环比模型精度更重要：PhotoPrism/Immich 的经验是"用户点两下就能改"比"模型 99%"更值钱。
  所以 `persons` 仓储必须提供 **合并 / 拆分 / 改名** 三件套（已实现，见 §3.2 下方仓储说明）。

### 3.4 隐私（必须写进产品）

- 人脸 embedding 属于**生物特征数据**：只存本机库文件、**不联网、不上传、不导出**；
- 设置里提供「关闭人脸识别」与「清除全部人脸数据」；
- 首次开启时明确提示一次。

## 4. 已知坑（按重要性）

1. **EXIF 方向**：我们的解码器**不做 orientation**（画布不旋转是产品决策）。AI 取特征前必须自己按 EXIF 转，否则竖拍照片全躺倒 → 特征全错。⚠️ 这是最容易漏的一步。
2. **解码是瓶颈，不是 GPU**：批量走缩略图（长边 1024）而不是原图，多线程解码，实测能快 3–5 倍。
3. **非方形图丢信息**：CLIP 224 中心裁剪会切掉竖构图主体；先按「短边缩放 + 中心裁剪」，主体偏边的图可做「中心+四角」多 crop 取平均（代价 ×3）。
4. **显存**：核显共享显存 512 MB–2 GB，batch 稍大就 OOM → **探测 + 动态降档**（8 → 4 → 1）。
5. **双显卡笔记本**：DirectML 可能默认跑核显 → 用 DXGI 枚举显式选高性能适配器。
6. **换模型必须整库重建**（向量空间变了），要做版本号 + 提示。
7. **增量**：`(image_id, size, mtime, 模型版本)` 都一样的跳过。
8. **卡阈值**：相似度低于 0.20 宁可不显示 —— "搜不到"比"搜错"体验好。
