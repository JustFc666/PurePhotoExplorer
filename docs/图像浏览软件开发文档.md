## 0.0 需求确认结果（v1.1 的架构依据）

三个关键问题已确认，直接改变了架构判断，先列在最前面。

### 确认一：万级规模 → 大幅简化，且可以做得更激进

| 维度 | 10 万级（原假设） | **万级（确认）** | 变化 |
|---|---|---|---|
| 向量检索 | HNSW 图索引 | **内存暴力余弦** | 1 万 × 1024 维 ≈ 40 MB 内存，余弦 < 10 ms。省掉 HNSW 全部复杂度与调参 |
| 建库时间 | 3 分钟 | **30 秒** | 可在首启后台静默完成，不需增量/分片 |
| AI 打标总耗时 | 数小时 | **约 20 分钟**（3B 模型 GPU） | 一次性可接受，无需复杂断点调度 |
| 元数据存储 | SQLite + 可能的分片 | **SQLite 单文件** | 万级 × 每条 1 KB ≈ 10 MB，进程内全量缓存 |
| 虚拟滚动 | 10 万节点基准 | 1 万节点基准 | 压力降一个数量级，但仍保留虚拟滚动（不因规模小而妥协架构） |

**结论：万级规模让"简单且快"成为可能。** 少一堆中间件、少一堆失败模式，这对"稳定优先"是净收益。架构不降级，只简化实现。

### 确认二：RAW 一期只浏览 → 但必须按"将来要开发"设计

这是 v1.1 最重要的架构约束。**最容易犯的错是：一期图省事，只写"提取嵌入式 JPEG 预览"，等二期要开发流程时发现解码层要重写。**

因此 RAW 层拆成**两个明确阶段**，一期只实现 Stage 1，但接口按两阶段设计：

| 阶段 | 能力 | 实现 | 何时做 |
|---|---|---|---|
| **Stage 1** | 提取 RAW 内嵌预览图 | `LibRaw::unpack_thumb()` — 纯拷贝不解码，**5–15 ms/张** | 一期（M2） |
| **Stage 2** | 去马赛克 + 完整开发流程 | `LibRaw::dcraw_process()` + 自研参数层 | 二期（预留） |

**关键设计约束**（违反即埋雷）：

1. **现在就用 LibRaw，不用 rawler 替代**。rawler 是纯 Rust 的 RAW 解析器，只做浏览够了；但它的像素输出是未去马赛克的 Bayer 阵列，二期要接完整开发流程时必须换库并重写解码层。LibRaw 一套 API 覆盖两阶段，避免二次返工。
2. **抽象 `RawPipeline` trait 隔离**，让 LibRaw 不泄漏到上层：
   ```rust
   trait RawPipeline {
       /// Stage 1：内嵌预览（不解码像素）
       fn extract_preview(&self, path: &Path) -> Result<PreviewImage>;
       /// Stage 2：完整去马塞克 → 线性 RGB f32（一期返回 Unsupported）
       fn develop(&self, path: &Path, params: &RawDevelopParams) -> Result<LinearImage>;
       fn probe(&self, path: &Path) -> Result<RawMetadata>;  // 两阶段共用
   }
   ```
3. **色彩管线从第一天就正确**。Stage 1 的内嵌预览是相机已经渲染好的 sRGB JPEG，直接用即可；Stage 2 输出必须是**线性 f32 RGB**。渲染层从一开始就按"线性输入 → 处理 → 转 sRGB 输出"设计，二期只需换输入源，不动下游。
4. **EXIF 从 Stage 1 就全量解析**（ISO/快门/光圈/镜头/机身序列号），二期开发流程直接复用这份数据建参数面板，不用二次解析 RAW。

### 确认三：防离线翻阅 → 容器内元数据与缩略图缓存都必须加密

威胁模型：攻击者拿到磁盘/文件副本（U 盘拷走、硬盘被拆、误发文件、备份泄露）。

**由此推出三条硬性要求，缺一条整个加密就形同虚设：**

| # | 要求 | 为什么容易被漏 |
|---|---|---|
| 1 | **文件名与大小必须加密** | 很多加密相册只加密图像像素，索引表用明文存原文件名。拿到盘的人一眼就知道里面是老板的客户合影 |
| 2 | **缩略图缓存不得明文落盘** ⚠️ | **本项目最大的坑**。§3 的 L2 磁盘缩略图库默认存明文 WebP，容器内图片的缩略图若照常落盘，攻击者翻目录就能看到全部内容，加密形同虚设。方案见 §3.5 |
| 3 | **不需防内存取证** | 威胁模型不含"运行中被人 dump 内存"，因此不必引入内存加密。**这大幅降低了实现复杂度，是本项目的实质收益** |

反过来说，**不需要**做：隐写（容器存在与否无所谓）、内存加密、反调试加固。省下的工作量投到稳定性上更划算。

## 0. 需求整理（原始需求 → 工程化拆解）

原始需求共 6 条，下面逐条翻译为带编号、可验收的功能需求与非功能需求。

### R1 支持多种图像格式

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-1.1 | 常见位图格式 | JPEG / PNG / BMP / GIF / TIFF / WebP / AVIF / JXL(解码可选)，单文件打开 ≤ 200ms（不含磁盘冷读） |
| FR-1.2 | 相机 RAW 格式（一期仅浏览） | Canon CR2/CR3、Nikon NEF/NEFR、Sony ARW/SR2、Fuji RAF、Adobe DNG、Pentax PEF、Panasonic RW2、Olympus ORF、Phase One IIQ。一期通过提取内嵌预览图实现，**接口预留完整开发流程**（见 §0.0 确认二） |
| FR-1.3 | 苹果生态格式 | HEIF/HEIC（含 10bit HDR）、AVIF，HEIC 必须能显示（iPhone 照片默认格式） |
| FR-1.4 | 分层格式 | PSD（Photoshop 合成预览）、AI（新版 PSD 变体）、TIFF 多页 |
| FR-1.5 | 格式探测 | 依据文件头 magic bytes 而非扩展名，扩展名错误时仍能正确识别 |
| FR-1.6 | 未知/损坏格式 | 不崩溃、不卡死，给出明确占位图与错误码 |
| FR-1.7 | RAW 开发流程（二期） | 去马赛克、白平衡、镜头校正、RAW 直出。**一期不实现，但架构必须已就位** |

**关键判断**：格式支持不能靠"逐个手写解码器"，必须依托成熟原生库（LibRaw / libheif / Wuffs / libvips），Rust 侧用 FFI 绑定。这是本项目最大的工程风险点，见 §8 风险 R-01。

**万级规模下的格式策略**：全量支持所有格式不现实也未必需要。实现顺序按"先覆盖用户 90% 实际使用"排：
1. **P0（一期必做）**：JPEG / PNG / HEIC / DNG / CR3 / NEF / ARW / WebP — 覆盖手机、相机主力、网页图
2. **P1（一期有余力做）**：TIFF / BMP / AVIF / PSD 预览 / RAF / RW2 / ORF / PEF
3. **P2（按需）**：CR2 / SR2 / IIQ / 相位检测 RAW / 中画幅特殊格式

未列入支持的格式**必须在界面上明确显示"暂不支持"**，而不是崩溃或静默失败。

### R2 浏览与编辑

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-2.1 | 单图浏览 | 全屏、缩放（滚轮以光标为锚点）、平移、旋转、对比模式（与上一张并排）、100% 像素查看 |
| FR-2.2 | 资源管理器式浏览 | 左侧目录树 + 右侧缩略图网格，虚拟滚动（Virtual Scroll），单目录 10 万张文件滚动不掉帧 |
| FR-2.3 | 视图模式 | 缩略图网格 / 大图标 / 详细信息列表 / 胶片条，布局可记忆 |
| FR-2.4 | 单图编辑 | 裁剪、旋转、翻转、亮度/对比度/饱和度/色温/色调曲线、HSL 局部调整、锐化、降噪、去马赛克、黑白转换、蒙版擦除 |
| FR-2.5 | 非破坏性编辑 | 所有编辑以操作栈（operation stack）形式记录在 XMP sidecar，原图永不修改，可随时回退 |
| FR-2.6 | 多图批量编辑 | 多选后应用统一预设，支持队列串行执行、进度显示、单项失败不中断整批、单次最大 500 张 |
| FR-2.7 | 格式转换 | 批量导出 JPEG/PNG/TIFF/WebP/AVIF/DNG，尺寸缩放、色彩空间转换（sRGB / Display P3 / Adobe RGB） |
| FR-2.8 | 元数据 | 读写 EXIF/IPTC/XMP，支持按相机/镜头/光圈/ISO/时间/GPS 筛选与排序 |

### R3 图像缓存

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-3.1 | 三级缓存架构 | L1 内存 LRU + L2 磁盘缩略图库 + L3 原图 mmap 局部解码 |
| FR-3.2 | 缓存键 | `hash(绝对路径 + 文件大小 + mtime_ns)`，文件被外部修改后自动失效 |
| FR-3.3 | 缓存预热 | 进入目录后按滚动方向预取前后各 1 屏，避免滚动白屏 |
| FR-3.4 | 容量控制 | 磁盘缓存上限可配置（**默认 5 GB**，万级四档全量约 5.7 GB，靠 LRU 淘汰冷档位），清理不影响正在浏览的条目 |
| FR-3.5 | 冷启动加速 | 二次启动直接加载缩略图库，不重新解码原图 |
| FR-3.6 | 完整性 | 强制关机后缩略图库不损坏，启动时自动校验与增量重建 |
| FR-3.7 | **容器内容缓存隔离** | **加密容器内图片的缩略图不得明文落盘**（见 §0.0 确认三要求 2、§3.5） |

> **万级规模的容量重算（实测值）**：1 万张 JPEG 均 6 MB → 原图约 60 GB。
> L2 缩略图库四档合计约 **600 KB/张**（WebP q82），1 万张约 **5.7 GB**。
> 因此默认上限设为 **5 GB**，只全量保留网格常用的前两档（256px + 512px，约 350 MB），
> 1024/2048 档位靠 LRU 按需重建。L1 内存 512 MB 足以容纳 1 万张 512px 缩略图（约 280 MB），
> 万级库可整目录一次性预热，省掉逐屏预取的复杂度。

### R4 大模型图像分析

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-4.1 | 模型接入 | 支持 Ollama / llama.cpp server 两种本地后端，HTTP 接口，可配置多端点 |
| FR-4.2 | 语义打标 | 批量分析产出结构化标签：主体、场景、颜色、情绪、文字内容、是否有人脸 |
| FR-4.3 | OCR | 提取图中文字（中文优先），写入全文索引 |
| FR-4.4 | 混合检索 | 关键词检索（SQLite FTS5）+ 向量语义检索（"海边的日落"能召回），结果融合排序 |
| FR-4.5 | 增量分析 | 只分析新增/变更文件，失败可续跑，模型不可用时不阻塞浏览 |
| FR-4.6 | 隐私 | 图片不出本机，模型端点可设为局域网地址，支持完全离线模式 |
| FR-4.7 | 批量效率 | **万级库全量分析约 20 分钟**（3B 模型 + GPU 加速），后台低优先级运行，不影响前台流畅度 |
| FR-4.8 | 人工修正 | 打标结果可在界面手工增删标签，修正后参与检索排序 |

### R5 加密文件夹

| 编号 | 需求 | 验收标准 |
|---|---|---|
| FR-5.1 | 容器格式 | 独立容器文件（`.pvault`），内部含文件级加密的条目目录 |
| FR-5.2 | 密码学 | AES-256-GCM + Argon2id 密钥派生，**不使用自研算法** |
| FR-5.3 | 密码解锁 | 启动后可输入密码解锁指定容器，解锁会话在内存中维持 |
| FR-5.4 | 自动锁定 | 空闲 15 分钟 / 手动锁定 / 切换用户 自动重新上锁 |
| FR-5.5 | 暴力破解抵抗 | 错误密码指数退避（2s→4s→8s…），KDF 参数可调 |
| FR-5.6 | 容器内浏览 | 解锁后容器作为一个普通目录出现在资源管理器视图，可正常预览与编辑 |
| FR-5.7 | 导入导出 | 文件拖入容器加密，导出需二次确认 |
| FR-5.8 | **元数据加密** | **文件名、大小、时间戳在索引中全部加密**（威胁模型要求，见 §0.0 确认三） |
| FR-5.9 | **缓存不泄露** | **容器内图片的缩略图缓存不得以明文形式落盘**（见 §3.5） |

**威胁模型明确说明（万级规模 + 防离线翻阅）**

| 攻击场景 | 是否防护 | 说明 |
|---|---|---|
| 拿到磁盘/U 盘/备份文件，用图片查看器直接打开 | ✅ 防护 | 密文，格式无法识别 |
| 拿到文件后读取文件名，看到"客户合影_张三.jpg" | ✅ 防护 | 索引整体加密，容器内无可见文件名 |
| 拿到文件后运行本软件暴力破解密码 | ⚠️ 部分防护 | Argon2id 显著抬高成本，但密码强度仍取决于用户 |
| 拿到文件后看到"有个 .pvault 文件，大小 2 GB" | ❌ 不防护 | **可接受**：威胁模型不含隐写，容器存在与否不是信息 |
| 运行中被人 dump 进程内存 | ❌ 不防护 | **可接受**：威胁模型不含内存取证，省下内存加密的复杂度 |
| 用户密码是 "123456" | ❌ 不防护 | 需 UI 侧强度提示与最低长度要求 |

> **范围裁剪的价值**：明确不做的三项（隐写、内存加密、反调试）合计能省下约 2–3 周工程量。这部分工作量投到 §9 稳定性保障上，对"稳定第一"更有价值。

见 §7 性能预算与 §9 稳定性保障。这条需求不是"性能好"，而是"性能指标可测量、不达标不允许发版"。

## 1. 技术选型

### 1.1 候选方案对比

| 维度 | **Tauri 2 + Rust（推荐）** | Electron + React | C# + WPF | Python + PySide6 |
|---|---|---|---|---|
| 空载内存 | 60–120 MB | 200–450 MB | 80–150 MB | 250–500 MB |
| 安装包体积 | 12–20 MB | 90–150 MB | 60–90 MB（自包含） | 80–200 MB |
| 冷启动 | 300–600 ms | 1.2–2.5 s | 500–900 ms | 1.5–3 s |
| 原生库接入 | FFI / bindgen | node-ffi / N-API | P/Invoke | Cython / ctypes |
| RAW 解码 | LibRaw FFI | LibRaw N-API | LibRawSharp | rawpy（C 扩展） |
| 图像处理 | `image` crate + rayon 并行 | Canvas / sharp | ImageSharp | Pillow / OpenCV |
| 硬件加速 | wgpu（GPU 渲染/编辑预览） | Chromium GPU | Direct3D | CUDA/DirectML |
| 前端生态 | 完整（与 Electron 相同） | 完整 | 需 XAML 重写 | 需 QSS 重写 |
| 开发效率 | 中（Rust 编译期成本） | 高 | 中高 | 高 |
| 长期稳定性 | 极高（无 GC、无运行时崩溃源） | 中（Node/Chromium 内存泄漏） | 极高（微软一等公民） | 中 |

### 1.2 选型结论

**采用 Tauri 2 + Rust + React/TypeScript。** 理由：

1. **直接命中 R6 第一原则。** 原生编译 + 无 GC，冷启动和内存占用比 Electron 低 3–4 倍，滚动 10 万张图不换页不掉帧是硬指标，不是优化项。
2. **格式支持需要 C 级库，FFI 是最短路径。** LibRaw / libheif / libvips 都有 C API，Rust bindgen 生态成熟（`rawler`、`libheif-rs`），而 Electron 侧要处理 node-gyp 交叉编译，Python 侧打包进 PyInstaller 体积会失控。
3. **UI 复用 Web 生态。** 大部分界面工作是布局与交互，用 TypeScript 写迭代速度远快于 XAML，且能直接引入现成的图片查看器/编辑器组件做二次改造。
4. **可编译到 macOS。** 若未来需跨平台，Rust 核心 + Web 前端可直接复用。

**不选 Electron 的决定性理由**：R6 把效率与稳定排在第一位，而 Electron 的架构决定了 200 MB 起跳的常驻内存和"用户开着不管也会变慢"的长期体验，这在"效率优先"的产品定位下是不可接受的。

### 1.3 核心依赖清单

| 领域 | 选型 | 说明 |
|---|---|---|
| 应用框架 | Tauri 2.5+ | Rust 内核 + 系统 WebView（Win10 用 WebView2） |
| 前端 | React 18 + TypeScript 5 + Vite 6 | 状态用 Zustand，避免 Redux 样板 |
| 虚拟滚动 | TanStack Virtual | 10 万条 DOM 节点只渲染可视区 |
| 图像解码 | `rawler`（LibRaw FFI）、`libheif-rs`、`image` crate、Wuffs | 常规格式走 `image`，RAW 走 LibRaw，HEIC 走 libheif |
| 图像处理 | `image` + `rayon` + `fast_image_resize` | SIMD 缩放与滤波 |
| 色彩管理 | `lcms2` FFI | sRGB/P3/Adobe RGB 转换 |
| GPU 渲染 | `wgpu` | 编辑器实时预览、缩放插值、批量导出加速 |
| 索引 | SQLite（`rusqlite`，bundled）+ FTS5 + `sqlite-vec` | 单文件、零部署 |
| 向量索引 | HNSW（`hnsw_rs` 或 sqlite-vec 内存表） | 百万级向量毫秒级召回 |
| 密码学 | `aes-gcm` + `argon2` + `rand` | 见 §5，禁止自研 |
| 哈希 | `blake3` | 缓存键与感知哈希 |
| 感知去重 | `img_hash`（pHash/dHash） | 相似图检索 |
| 状态持久 | `serde` + `bincode` | 预设、操作栈、配置 |

## 2. 总体架构

### 2.1 分层

```
┌─────────────────────────────────────────────────────────────┐
│  L5 表现层  React 18 + TypeScript                            │
│      单图查看器 / 缩略图网格 / 编辑器面板 / 批量队列 / 锁屏页  │
├─────────────────────────────────────────────────────────────┤
│  L4 交互层  Tauri Command / Event 桥                          │
│      双向类型安全 IPC，全部调用 async，UI 永不阻塞              │
├─────────────────────────────────────────────────────────────┤
│  L3 领域层  Rust 纯逻辑（可单测，无 IO）                        │
│      格式探测 / 操作栈 / 筛选查询 / 编辑预设 / 检索打分         │
├─────────────────────────────────────────────────────────────┤
│  L2 服务层  Rust 运行时服务                                     │
│      扫描器 · 解码器 · 缓存管理 · 缩略图库 · 索引             │
│      AI 打标器 · 容器加密服务 · 导出管线                        │
├─────────────────────────────────────────────────────────────┤
│  L1 基础层  原生库 FFI / 文件系统 / SQLite / GPU(wgpu)         │
│      LibRaw · libheif · lcms2 · aes-gcm · argon2 · SQLite     │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 进程与线程模型

稳定性第一的关键：**解码永远不在 UI 进程里做。**

```
┌──────────────────────┐
│  主进程 (Rust Core)   │  状态机、索引、IPC、加密、调度
│  线程池: 1 调度 + N-2 工作线程 │
└──────────┬───────────┘
           │
           ├── 扫描线程 ×1        目录遍历，yield 式可中断
           ├── 解码线程池 ×(N-2)  rayon，缩略图解码
           ├── AI 任务 ×1         串行，可暂停，不抢解码资源
           └── 渲染/GPU 线程 ×1   wgpu 独立
```

- **解码池与 AI 任务互斥优先级**：用户正在滚动时 AI 自动降为最低优先级（`rayon` 池用优先级队列，非抢占式）
- **IPC 全部 async**：任何超过 16ms 的操作不得在 IPC 同步调用里做
- **背压机制**：解码队列超过 200 项时丢弃远离视口的低优先级请求

### 2.3 IPC 契约原则

- 所有 Tauri Command 参数与返回值用 TypeScript 类型 + Rust 结构体双向生成，禁止手写字符串命令
- 大数据传输（像素缓冲）走自定义二进制协议，不走 JSON
- 事件通道分命名空间：`img://`、`cache://`、`scan://`、`ai://`、`vault://`

## 3. 缓存子系统设计

这是 R3 的实现核心，直接决定"效率"体感。

### 3.1 三级缓存

| 级 | 位置 | 内容 | 容量 | 典型命中延迟 |
|---|---|---|---|---|
| L1 | 内存 LRU（`lru` crate） | 解码后 512px 缩略图 RGBA + 元数据 | 默认 512 MB，可配 | < 1 ms |
| L2 | 磁盘缩略图库 | WebP 质量 82 的多档缩略图（256/512/1024/2048） | 默认 20 GB，LRU 淘汰 | 3–15 ms |
| L3 | 原图 mmap | JPEG 走 `jpeg-decoder` 缩放解码；RAW 走 LibRaw half-size 预览 | 依赖 OS 页缓存 | 20–200 ms |

### 3.2 缓存键与失效

```
cache_key = blake3( 绝对路径 || file_size || mtime_ns )[0..16]
缩略图文件名 = {cache_key}-{尺寸档位}.webp
元数据行 = (cache_key, path, size, mtime_ns, width, height, 档位, 访问时间, 字节数)
```

- 文件被外部修改 → `mtime_ns` 或 `size` 变化 → 键自动变化 → 旧条目变孤儿，由 LRU 清理回收
- 启动时跑一次一致性校验：抽样 1% 条目核对 mtime，不一致即标记删除
- **解码失败不缓存**，避免坏图被反复重试

### 3.3 预取策略

```
视口可视区 [0..N] → 立即请求（优先级 0）
向上/向下各 1 屏 → 预取（优先级 1）
向上/向下各 3 屏 → 预取（优先级 2，可中断）
其余 → 不请求
```

滚动方向变化时立即翻转预取方向。缩略图网格滚动时用 `IntersectionObserver` + 位置预测。

**万级规模优化**：1 万张全部缩略图在磁盘缓存中合计约 1.6 GB，**可一次性全量预热到 L1 内存**（512 MB 足够放下 512px 档位）。因此万级库可以走"整目录一次性预热"策略，省掉逐屏预取的复杂度——但预取代码仍要保留，因为二期规模可能上 10 万。

### 3.4 RAW 缩略图的特殊路径

一期 RAW 只做浏览（§0.0 确认二 Stage 1），路径与其他格式不同，**优先取内嵌预览而不是全量解码**：

```
其他格式：解码原图 → 缩放 → 缩略图
RAW 格式：LibRaw::unpack_thumb() → 内嵌 JPEG（相机已渲染好）→ 缩放 → 缩略图
                     ↓ 失败时（少数机型无内嵌预览）
                  降级：LibRaw::dcraw_process(half_size) → 缩放
```

性能差异极大：内嵌预览 **5–15 ms/张**，half-size 去马赛克 **200–500 ms/张**。优先内嵌预览让 1 万张 RAW 的首次建库从数小时降到数分钟。

### 3.5 容器内容的缓存隔离（安全关键，必做）

威胁模型要求「防离线翻阅」（§0.0 确认三）。**如果按普通图片的思路实现缓存，容器加密会被绕过**：

```
❌ 错误做法（会让整个加密功能形同虚设）
   用户浏览 .pvault 容器
     → L2 缩略图库写入 C:\...\thumbs\{hash}.webp   ← 明文！
     → 攻击者拷贝整个用户数据目录
     → 打开 thumbs 目录，所有图片一览无余

✅ 正确做法
   容器内缩略图按容器主密钥加密后落盘
     C:\...\thumbs\vault-{container_id}\{entry_uuid}.enc
   容器 ID 与条目 ID 用随机 UUID（不泄露文件名）
   缓存记录在 SQLite 标记 is_encrypted = 1
   写入前检查：源路径属容器 → 一律走加密分支
```

| 项 | 方案 |
|---|---|
| 存储路径 | 独立子目录 `thumbs/vault-{uuid}/`，不与普通缩略图混放 |
| 文件名 | `{entry_uuid}.enc`，不含原名、不含原路径 |
| 加密 | AES-256-GCM，主密钥由 Argon2id 派生，**每条目独立 nonce** |
| 缓存键 | 容器内容用 `(container_id, entry_uuid)` 而非路径哈希 |
| 解密时机 | 仅在解锁会话内、仅在内存中解密供显示，**明文不落盘** |
| 锁定清理 | 锁定时删除该容器全部 L1 缓存条目 |
| 校验 | 单测必须覆盖「解锁→浏览→锁定→检查磁盘无明文」全链路 |

> **这条要有独立的集成测试**，因为它的失败是静默的——功能看起来完全正常，只是安全性没了，普通测试不会报错。

### 3.6 首次索引（万级规模）

- 启动后台扫描用户配置的根目录，**流式写入 SQLite**，UI 立即可用
- 扫描用 `notify` crate 监听变更，WAL 模式 + 每日增量
- **1 万张建库目标 < 30 秒**（仅建记录 + 解析 EXIF，不含图像解码）
- 万级规模下元数据约 10 MB，**全量常驻内存**，查询零 IO，检索响应 < 10 ms

## 4. 图像处理与编辑

### 4.1 非破坏性编辑模型

所有编辑表示为可序列化的操作栈，写入 XMP sidecar（`IMG_1234.jpg.xmp`）：

```rust
struct EditOp {
    op: EditOpKind,        // Crop | Rotate | Flip | Exposure | Contrast | Saturation
                           // | Temperature | Tint | Curve | HslAdjust | Sharpen
                           // | Denoise | Monochrome | MaskErase
    params: serde_json::Value,
    mask: Option<MaskRef>,  // 可选蒙版：路径 + 羽化 + 不透明度
}

struct EditStack {
    base: FileFingerprint,  // 绑定原图指纹，原图变更则操作栈失效并警告
    ops: Vec<EditOp>,       // 有序，栈顶为最后应用
    updated_at: i64,
}
```

### 4.2 渲染管线

```
原图解码 → 线性化（去 Gamma）→ 应用操作栈（Float32 RGBA）
   → 色阶/曲线（lut32 查找表）→ 色彩空间转换（lcms2）→ 编码 sRGB → 显示/导出
```

- 编辑预览：先按缩放比例渲染，滚动/缩放时降级到 mipmap 层，松手后再上全分辨率
- GPU 加速：曲线、HSL、锐化等逐像素操作编译成 wgpu compute shader，批处理时吞吐提升明显
- 所有浮点运算在 16bit 精度下进行，避免批量处理累积误差

### 4.3 批量编辑

```
选图 → 选预设 → 抽样 3 张即时预览（用户确认外观）
     → 入队 → 串行执行（每张独立事务）
     → 失败项汇总报告，可单独重试
```

- 预设（preset）本身是操作栈的子集 + 参数约束，存 JSON，可导入导出
- 队列可暂停/继续/取消；单张失败不中断，写入 `errors.json`
- 默认输出到独立目录，**绝不原地覆盖原图**；用户显式选择"覆盖"时先建 `.bak`

## 4A. RAW 两阶段扩展设计（一期只做 Stage 1，为二期留口）

> 这是 v1.1 新增章节。用户确认"一期只浏览，后续可能开发完整流程"，因此**接口现在就要按两阶段设计**，否则二期必然重写解码层。

### 4A.1 阶段划分

| | **Stage 1（一期）** | **Stage 2（二期预留）** |
|---|---|---|
| 能力 | 提取 RAW 内嵌预览图 | 去马赛克 + 白平衡 + 镜头校正 + 直出 |
| LibRaw API | `open_file()` + `unpack_thumb()` + `dcraw_process(half)` | `dcraw_process()` + `imgdata.params.*` |
| 输出 | sRGB 8bit JPEG（相机已渲染好） | **线性 f32 RGB**（未做 gamma） |
| 单张耗时 | 5–15 ms（内嵌预览）/ 200–500 ms（降级路径） | 1–3 s（24MP） |
| 用途 | 缩略图、单图浏览、EXIF 展示 | 完整开发流程、RAW 直出、批量处理 |

### 4A.2 接口定义（一期就按此实现）

### 4A.3 一期就必须做对的三件事

| # | 做什么 | 不做的后果 |
|---|---|---|
| 1 | **用 LibRaw，不用 rawler 替代** | rawler 只输出未去马赛克的 Bayer 阵列，二期换库要重写整个 RAW 解码层 |
| 2 | **渲染层从第一天就按"线性输入"设计** | 二期要重构整条色彩管线（sRGB 假设贯穿全代码） |
| 3 | **`probe()` 全量解析 EXIF** | 二期开发流程要重复解析 RAW，且 EXIF 解析逻辑会散落各处 |

### 4A.4 色彩管线预留

```
                    Stage 1 路径              Stage 2 路径（二期）
                    ───────────              ────────────────
输入         内嵌 sRGB JPEG            →  线性 f32 RGB (LibRaw)
                      ↓                          ↓
              sRGB → 线性 (去 Gamma)      （已在线性域）
                      ↓                          ↓

```

## 5. 加密容器设计

### 5.1 密码学方案（不自研）

| 环节 | 算法 | 参数 |
|---|---|---|
| 密钥派生 | Argon2id | m=64 MiB, t=3, p=1（可配置，最低 32 MiB） |
| 文件加密 | AES-256-GCM | 每条目独立 96-bit nonce，认证标签 128-bit |
| 索引加密 | AES-256-GCM | 整表加密，含条目名、大小、时间戳 |
| 随机数 | `rand` crate → OS CSPRNG | 禁止任何 `Random::new()` 种子时间 |
| 完整性 | GCM tag 校验 + 容器头 HMAC | 校验失败即拒绝，不降级 |

> **安全红线**：密码学全部交给成熟 crate，只做组装。任何"自己写 AES"的改动都必须被 review 拒绝。错误密码走指数退避，容器头内不含可用于密码验证的明文信息。

### 5.2 容器格式

```
┌──────────────────────────────────────────┐
│ Header (4 KiB, 明文)                      │
│  magic "PVLT" | version | kdf params      │
│  salt(32) | nonce_base(12) | header_mac    │
├──────────────────────────────────────────┤
│ Index Block (加密, AES-256-GCM)            │
│  [ {name, size, mtime, offset, len,       │
│     iv, thumbnail_offset, thumb_len}, ... ]│
├──────────────────────────────────────────┤
│ Entry 0: name(加密) | iv | ciphertext | tag │
│          └ 缩略图块（可仅存低清，缩小容器）   │
│ Entry 1: ...                              │
├──────────────────────────────────────────┤
│ Entry N                                    │
└──────────────────────────────────────────┘
```

### 5.3 会话与锁定

- 解锁 → 主密钥驻留内存（`Vec<u8>`，解锁后清零、进程退出时 `zeroize`）
- 自动锁定触发：系统休眠/锁屏（Windows `WTS_SESSION_LOCK`）、空闲 15 分钟、手动锁定
- 锁定后清空密钥并把容器内所有缩略图从内存缓存驱逐
- 容器内的图在资源管理器视图中以 `🔒` 前缀展示，与普通目录视觉区分

## 6. AI 检索子系统

### 6.1 架构

```
待分析队列 ──► 缩略图取用(L2 512px) ──► VLM 推理(本地 HTTP)
                                              │
                                    ┌─────────┴─────────┐
                                    ▼                   ▼
                             结构化 JSON          文本 + 向量
                          {标签,主体,场景,颜色,      │      │
                           情绪,有无人脸}           │   Embedding
                                    │                │      │
                                    ▼                ▼      ▼
                             SQLite tags 表    FTS5 全文    HNSW 向量
                                    └────────┬───────┘      │
                                             ▼              ▼
                                      混合检索打分融合（RRF）
                                             ▼
                                        排序结果
```

### 6.2 模型建议

| 用途 | 模型 | 说明 |
|---|---|---|
| 主 VLM | Qwen2.5-VL-3B/7B (Q4_K_M) | 中文描述质量好，本地 Ollama 直接拉取 |
| 轻量打标 | Florence-2-base | 速度快，适合大库粗筛 |
| Embedding | bge-m3 或 nomic-embed-text | 中文检索效果佳，512–1024 维 |
| OCR | PaddleOCR / RapidOCR（可选） | 中文识别准确率高 |

**降级链**：Ollama → llama.cpp server → 云端 API（需显式开启并显示警告）→ 关闭（仅关键词检索可用）。任何一级失败都不得阻塞浏览功能。

### 6.3 混合检索与打分（万级简化方案）

- 关键词：SQLite FTS5（`unicode61` + 自定义中文 bigram 分词器，规避依赖 `jieba`）
- 语义：**内存暴力余弦检索**。1 万条 × 1024 维 f32 ≈ 40 MB 内存，一次全量点积约 1000 万次乘加，**< 10 ms**，完全够用
- 融合：Reciprocal Rank Fusion，`score = Σ 1/(60 + rank_i)`
- 前端支持"以图搜图"：上传或框选一张图 → 取其向量 → 最近邻

> **规模与检索结构的对应关系**（供二期参考，避免过早优化）：
>
> | 规模 | 语义检索方案 | 理由 |
> |---|---|---|
> | **≤ 2 万（本项目）** | **内存暴力余弦** | 10 ms 内，零依赖，零调参，零失败模式 |
> | 2 万 – 20 万 | HNSW（`hnsw_rs`） | 暴力余弦开始变慢，HNSW 召回率需调参 |
> | > 20 万 | 磁盘 HNSW / 专用向量库 | 内存放不下，需持久化索引 |
>
> 万级规模用暴力余弦是**净收益**：省掉 HNSW 的构建、持久化、召回率调参、增量更新四类失败模式。

| 崩溃率 | 0（核心流程） | 内部测试矩阵 500 次操作 | 是 |
| 崩溃恢复 | 不丢索引、不丢预设 | 强杀进程后重启验证 | 是 |
| 单文件解析失败 | 不得导致整体不可用 | 注入 100 个损坏文件 | 是 |
| **容器加密不泄露** | **磁盘零明文** | 集成测试：浏览后全盘扫描无明文缩略图与文件名 | 是 |

## 9. 稳定性保障

### 9.1 崩溃隔离

| 异常场景 | 表现 | 处理 |
|---|---|---|
| 单文件解码失败 | 该图显示占位符 | 捕获，记 `decode_error` 日志，继续其他文件 |
| 原生库 panic | 可能导致进程崩溃 | `catch_unwind` 包裹 FFI 调用 + 该文件降级 |
| 内存不足 | 分配失败 | 全局 `set_alloc_error_hook`，L1 缓存主动清空后重试一次 |
| SQLite 损坏 | 索引不可用 | 每日 `.bak`，损坏时自动回滚并重建 |
| 容器密码错误 | 无法解锁 | 指数退避 + 提示，不写入任何可疑状态 |
| 前端渲染异常 | 白屏 | React ErrorBoundary 包裹每个页面，降级到基础列表视图 |

### 9.2 测试策略

| 层级 | 工具 | 覆盖目标 |
|---|---|---|
| Rust 单元测试 | `cargo test` | 领域层纯逻辑 ≥ 80% |
| Rust 集成测试 | `cargo test --test integration` | 容器加解密往返、缓存键、索引 CRUD |
| 前端组件测试 | Vitest + Testing Library | 关键交互 ≥ 60% |
| E2E | Playwright（Tauri 驱动） | 主干用户旅程 12 条 |
| 格式兼容性 | 固定测试图库（≥ 300 张，覆盖 40+ 相机型号 RAW） | 每种格式一条 smoke |
| **RAW 内嵌预览** | 每相机型号一条：验证 `unpack_thumb` 成功且耗时 < 20 ms | 无内嵌预览的机型走降级路径 |
| **加密防泄露** | 解锁→浏览→锁定→**全盘扫描无明文缩略图与文件名** | 安全关键，失败静默，必测 |
| 性能回归 | 脚本化基准（冷启动/建库/滚动/解码/检索/解锁） | 每次发版跑，超阈值 10% 即告警 |
| 模糊测试 | `cargo-fuzz` 解码器与容器解析 | 每周一次夜间任务 |

### 9.3 稳定性机制

- **看门狗**：解码任务超时 10 s 强制中断（`rayon` 作用域 + 取消 token）
- **优雅退出**：`Ctrl+C` / 关窗时等待队列落盘，最多 3 s，超时强制退但保证 SQLite WAL 不损坏
- **日志**：滚动日志（10 MB × 5），默认脱敏（不记录文件路径明文，除非 debug 模式）
- **崩溃上报**：可选、默认关闭、本地落盘不外传

## 13. 开发顺序（按依赖度重排）

完整规划见独立文档 **`docs/开发顺序规划.md`**。此处给出结论摘要。

### 重排的核心依据

原 §10 按功能需求顺序推进，会导致 **M0 就要面对 LibRaw 编译**，
一旦 MSVC 装不上整条路线卡死。重排后：

| 变化 | 说明 |
|---|---|
| **单图浏览提为第一个里程碑** | 它是整个项目的最小完整闭环：一次性打通格式探测 → 解码 → 缓存 → IPC → 渲染 |
| **S1/S2 完全不依赖 MSVC** | 纯 Rust 后端（jpeg-decoder / png / fast_image_resize）即可支撑单图浏览与资源管理器 |
| **S3（RAW/HEIC）后置** | 唯一被 MSVC 阻断的阶段，排在能用软件之后 |
| **S6（加密）可并行** | argon2 / aes-gcm 均有纯 Rust 实现，与 S1→S2 无依赖 |

### 阶段序列

```
S0 地基 ✅ 已完成（81 测试全绿）
  ↓
S1 单图浏览 ⭐ 1.5 周 ← 解码层已完成，剩 Tauri 壳 + 画布
  ↓
S2 资源管理器 2 周
  ↓
S3 RAW 与 HEIC 2 周 ⚠️ 需 MSVC
  ↓
S4 单图编辑 3 周
  ↓
S5 批量导出 2 周
  ↓
S7 AI 检索 2 周（依赖 S2）

S6 加密容器 2 周 ← 无依赖，可全程并行
S8 RAW 开发流程 3 周 ← 架构已就位，填实现即可
```

**S1→S3 结束（约 5.5 周）即可交付"格式全、浏览快"的软件。**
