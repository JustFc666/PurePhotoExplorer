# 一个照片管理器是怎么造出来的

> 这份说明写给**不学计算机**的读者。
> 目标不是让你会写代码，而是让你看完之后能说清楚：这软件由哪几块组成、每块在干什么、为什么要这么干、哪些地方是真的难。
>
> 全篇尽量避免行话。实在绕不开的，第一次出现时会用括号解释，文末还有一张「名词小抄」。

---

## 0. 先说它是干什么的

**PurePhotoExplorer 是一个装在 Windows 上的照片管理工具。**

你可以把它想成一个"图书馆管理员"：

- 你的照片散落在 D 盘、E 盘、移动硬盘的几十个文件夹里 → 它负责**登记造册**，建一份目录卡片；
- 你想找"去年在杭州拍的、带猫的照片" → 它负责**按条件查卡片**，不用真的去翻硬盘；
- 你想看看某张照片拍得好不好 → 它负责把照片**缩成小图快速铺给你看**，你点开哪张才去读原图；
- 你想给照片打标签、认人脸、改曝光、裁一刀 → 它负责**动手改**，而且保证改坏了原图也不会丢。

听起来简单。但真正做起来，难点全在三个地方：**文件格式特别多**、**照片特别大**、**"看起来瞬间出图"其实很费劲**。

下面按顺序讲：软件分成哪几层 → 代码怎么分家 → 一张照片从硬盘到屏幕的完整旅程 → 五个有意思的算法 → 工程上踩过的坑。

## 1. 整体结构：三层，各管各的

```
┌──────────────────────────────────────────────────────────┐
│  界面层（你看到的窗口）                                     │
│  React + TypeScript · 23,178 行                          │
│  图库网格 / 查看器 / 侧栏 / 右键菜单 / 各种弹窗             │
└───────────────────────────┬──────────────────────────────┘
                            │  只通过 92 个「命令」喊话
                            │  （不直接碰硬盘，不直接碰数据库）
┌───────────────────────────▼──────────────────────────────┐
│  大脑层（Rust 写的后端）                                    │
│  13 个 crate · 37,590 行                                 │
│  解码图片 / 读 EXIF / 建索引 / 跑 AI / 改文件               │
└───────────────────────────┬──────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────┐
│  仓库层                                                   │
│  ① SQLite 数据库（16 张表）—— 目录卡片                     │
│  ② 缩略图缓存目录 —— 小图副本                              │
│  ③ 你的原始照片 —— 只读，除非你主动改                       │
└──────────────────────────────────────────────────────────┘
```

**为什么要分层？**

因为"界面"和"干活"的节奏完全不一样。

界面要做到**点了就有反应**（哪怕只是转个圈），所以它不能干重活——一旦在主界面上解码一张 50MB 的 RAW，整个窗口就会卡住，看起来像死机。

而干活的部分要**尽量快**，还要**不能崩**（一个损坏的 JPEG 不能让整个软件退出）。

所以两边分开：界面负责"好看 + 响应"，后端负责"算得快 + 算得稳"，中间用一条固定的通道说话。

这条通道很重要，值得解释一下它为什么存在：

> **界面层不能直接读硬盘。**
> 在浏览器里，网页是被"关在笼子里"运行的（这个笼子叫沙箱），碰不到你电脑上的文件。
> 这个软件的窗口本质上也是个网页（用 Tauri 打包成了桌面程序），所以它同样碰不到硬盘。
>
> 想读一张照片，界面必须发一句请求——"请把 D:\照片\01.jpg 的缩略图给我"——后端收到、干完活、把结果递回去。
> 这样的请求现在有 **92 种**，全部写在 `apps/desktop/src/ipc/` 目录里。
>
> 好处是：所有碰硬盘、碰数据库的动作都集中在后端这一处，出了问题只要查一个地方。坏处是：每次来回都要"打包—传输—解包"，所以传大块数据时要想办法省事（后面会讲缩略图怎么取巧）。

## 2. 为什么用 Rust 写后端、React 写界面

先说这两个东西是什么。

**Rust** 是一门编程语言，特点是**跑得快**而且**几乎不会因为内存用错而崩溃**。它的规矩特别严，编译的时候就把很多错误拦住了。

**React** 是一个做界面的工具库，特点是**数据一变，界面自动跟着变**，不用手动去改每一个像素。

为什么这么配？

| 需求 | 谁来做 | 为什么 |
|---|---|---|
| 解码 JPEG / RAW / HEIC | Rust | 解码一张 2400 万像素的照片要做几亿次运算，慢一点就是"卡成幻灯片"。Rust 跟 C 一个速度，但不会像 C 那样一不小心访问了不该访问的内存。 |
| 界面上几百张缩略图的滚动、选中、拖拽 | React | 这些是"状态变化"，React 的模型很贴：你只改数据，它负责把界面刷新到对的样子。 |
| 读文件、写文件、改 EXIF | Rust | 要处理"写一半断电了怎么办"，这类事必须做得非常严谨。 |
| 让窗口长得好看 | React + CSS | 网页技术做界面最快也最灵活。 |

一句话：**重活交给 Rust（快），花活交给 React（好改）。**

## 3. 代码怎么分家：13 个"车间"

37,590 行 Rust 如果全塞一个文件里，没人看得懂。所以按"职责"切成 13 个独立的包（Rust 里叫 crate，可以理解成**车间**，每个车间只做一类活，有自己的大门和出货口）。

| 车间 | 干什么 | 行数 |
|---|---|---|
| `pv-decode` | **解码**：把 17 种图片格式变成像素，把照片缩小 | 8,782 |
| `pv-index` | **目录卡片**：SQLite 里的 16 张表，谁增谁删谁查 | 4,658 |
| `pv-store` | **仓库总管**：把"解码"和"索引"粘起来，对上提供服务 | 3,612 |
| `pv-meta` | **EXIF**：读出拍摄时间/相机/光圈/GPS，写回方向标记 | 2,235 |
| `pv-ai` | **AI**：打标签、识别人脸、聚类人物 | 2,050 |
| `pv-scan` | **扫描**：遍历文件夹，找出所有图片，判断是否变过 | 1,359 |
| `pv-core` | **公共语言**：格式判断、像素容器、几个基础类型 | 1,115 |
| `pv-archive` | **压缩包**：zip / 7z / cbz 里的图片 | 1,015 |
| `pv-cache` | **缓存**：内存里留热图（L1）、磁盘上存小图（L2） | 483 |
| `pv-lib` | **图库概念**：图库、智能图库的增删改 | 460 |
| `pv-geo` | **地名**：经纬度 → "杭州市西湖区" | 380 |
| `pv-edit` | **编辑**：旋转、翻转、裁剪后写回文件 | 336 |
| `pv-vault` | **加密图库**：加锁的那种图库 | 275 |

再往上一层，`apps/desktop/src-tauri/` 是"总装车间"——它把 13 个车间拼起来，对外提供那 92 个命令。

前端也这么分：

```
src/
├── App.tsx              组合根：把各个零件装到一起（几百行，不长）
├── hooks/               行为逻辑：useManager（图库状态）、useImageView（查看器）、
│                        useShortcuts（快捷键）…… 一个文件一件事
├── ipc/                 唯一出口：所有跟后端说话的函数都在这
├── components/
│   ├── manager/         图库视图：网格、列表、侧栏、筛选、状态栏
│   ├── viewer/          单张查看器：缩放、裁剪、打印预览
│   └── chrome/          通用零件：右键菜单、确认框、输入框
└── constants/           常量：支持的格式清单等
```

**这个"分家"不是一开始就这样的。** 最初图库视图是一个 2168 行的巨型文件，改一个小地方要滚半天。后来按"一次只搬一块、搬完就验证"的节奏，拆成了现在十几个小文件（这次拆分后面第 8 节会讲，因为它暴露了两个真 bug）。

## 4. 一次「点开文件夹」的完整旅程

这是全篇最值得看的一节。**你点一下鼠标，到看见缩略图，中间发生了什么。**

假设你点了左边侧栏的 `D:\照片\2024杭州`。

### 第 1 步：界面问后端"这个目录里有什么"

界面发出命令 `fs_list_images`，参数是路径。

### 第 2 步：后端扫目录，只认后缀名，不读内容

遍历这个文件夹，按扩展名筛出图片文件。**这一步不打开任何文件**——打开 500 个文件头去判断类型要好几秒，而你现在只是想看看列表。

代价是：一个叫 `.jpg` 但其实是文本的文件会被误列。可以接受，因为打开时会再校验一次（那时才读文件头那几个字节，也就是"魔数"）。

### 第 3 步：后端回一份"清单"

每条记录包含：文件名、大小、修改时间、是否在索引里。界面拿到后立刻把格子铺出来——**这时候格子里还是空的，只有一个占位框**。

这一步只花了二三十毫秒。**"看起来很快"的第一个秘密就在这里：先把框摆出来，图慢慢填。**

### 第 4 步：界面按"谁快要看见"排队要缩略图

不是一次性要 500 张。而是：

1. 只算**当前屏幕上真的看得见**的那几十张（用一个叫 `useInView` 的机制判断）；
2. 再加**后面差不多两屏**的 30 张做预取（你往下滚的时候不会白屏）；
3. 丢进一个有 **4 个位置**的队列（`thumbQueue`），同时最多只跑 4 个请求。

为什么要限 4 个？因为解码是 CPU 密集的活，开 20 个同时跑只会互相抢，反而全部变慢；而且会把风扇吹起来。

### 第 5 步：后端找缓存，命中就直接返回

每张缩略图都有一个"身份证号"（缓存键），算法是：

```
缓存键 = 哈希(磁盘卷的唯一编号 + 相对路径 + 文件大小 + 修改时间)
```

注意这里**没有用盘符**（`D:` 这种）。为什么？因为你的移动硬盘今天插上是 `D:`，明天可能是 `E:`。如果按盘符算，换个接口就全部失效，白算一遍。

用"卷的编号 + 从卷根开始的相对路径"就稳了：盘符变了，身份不变。

### 第 6 步：没命中缓存 → 真的去解码

这一步是全场最费劲的，细节在第 5 节讲。

### 第 7 步：把像素递回界面——不走"文字"，走"裸字节"

一般的做法是把图片变成一段文本（base64 编码），塞进请求结果里。缺点是**体积膨胀 33%**，而且编码解码两头都要花时间。

这个项目走的是另一条路：直接把像素字节流递回去，走的是专门的通道（`tauri::ipc::Response`）。

> 为什么要专门提这件事？因为这条路有个前提：窗口的**安全策略**必须允许它。
> 项目里那段配置（CSP，可以理解成"网页的白名单"）必须写着允许 `ipc:` 通道，
> 否则浏览器会直接把这条数据流掐掉——表现就是"图一块也出不来"，而且不报错。
> 这个坑有专门的测试守着（`anim_protocol.rs`）。

### 第 8 步：界面把字节画进格子

拿到的是原始像素，用 canvas（网页里的画布）画上去。

**为什么不用 `<img>` 标签直接给个文件路径？** 因为那样做每次滚动都要重新解码，而且没法统一处理"这张图是横向的还是竖向的"（EXIF 方向的问题，见 5.2）。

---

到这里，你已经看到图了。

**如果你点的是"加入图库"而不是"点开看看"，流程会多出一大截**：遍历（这次真的读每个文件）、算指纹、判断新增/修改/删除、写进数据库、生成缩略图存到缓存目录。这部分在 `pv-scan` 和 `pv-store` 里。

**这里有个刻意的设计**：浏览 ≠ 入库。

- 左键点文件夹 = **只是看看**（只读，不写数据库，不写缓存）
- 右键「加入图库」 = **真的登记**（写索引、算缓存、以后能搜索能打标）

为什么分开？因为"随手看看"是高频动作，如果每次看一眼都往数据库里塞 500 条记录，索引会迅速膨胀，而且你根本没打算管理那些照片。

## 5. 五个值得讲的算法

### 5.1 缩略图：为什么不能"先解码再缩小"

这是整个项目**性能上最关键的一个决定**，值得展开讲。

一张 2400 万像素的照片，解码出来是这样一块内存：

```
6000（宽） × 4000（高） × 3 个字节（红绿蓝） = 72,000,000 字节 ≈ 72 MB
```

而你只需要一张 236 像素宽的小图。如果老老实实"整张解码 → 再缩小"，等于为了一个 200KB 的小图，先吃掉 72MB 内存、算完 2400 万像素。

**更聪明的做法是：让解码器一开始就只解一部分。**

以 JPEG 为例，这种格式把图片切成 8×8 的小块压缩。解码器支持一种"跳着解"的模式（业界叫 DCT 缩放）：只取每 8 个块里的 1 个，直接得到 1/8 大小的图。这样：

```
6000 × 4000  →  750 × 500（只解 1/64 的像素量）
```

**内存从 72MB 降到 1MB 出头，速度快 10 倍以上。**

关键在于：**这个"跳着解"必须发生在"格式自己的空间里"，不能等转成了通用像素格式之后再做。** 一旦转成通用格式（RGBA），就已经吃过 72MB 了，再缩小也来不及。

> 项目里有一条硬规矩写在这块代码的注释里：
> **降采样要在源格式的空间里做完，再转成通用像素。⛔ 不要先转整幅 RGBA。**
> 这条规矩是踩过坑才写下来的——早期版本就是这么写的，打开一个大目录时内存飙到几个 GB。

还有一个小细节：缩小本身也是个算法活。简单的"取最近的点"会出锯齿，好的做法是按面积加权平均。项目用了一个专门的库（`fast_image_resize`），并且**必须开启它的多线程特性**——不开的话，一张图缩小要 40ms，开了之后 5ms。

### 5.2 EXIF 方向：为什么"旋转照片"可以不动一个像素

手机拍照时，感光元件是固定方向的。你竖着拿手机拍，实际记录下来的图像是横的，然后相机会在文件里写一个标记：

```
Orientation = 6   （意思是"显示的时候顺时针转 90 度"）
```

**照片的像素一个都没动，只是加了一句话。**

这个设计的好处是：旋转零成本，不损失画质（重新编码一次就掉一点质量）。

坏处是：**每个读照片的程序都必须尊重这句话。**

这个项目里，方向标记在三个地方被处理：

1. **显示时**：解码后按标记旋转像素，再画到屏幕上；
2. **编辑时**：你点"顺时针旋转"，程序是**真的重新编码**了一次（因为要保存成你看到的样子），同时把标记改成 `1`（表示"正常，不用转了"）；
3. **写回时**：⚠️ 这里有个真陷阱，见 7.2。

> 还有一个容易忽略的点：**只有当用户真的旋转过，才把标记置 1。**
> 如果程序"好心"地在每次保存时都把方向"摆正"并置 1，那用户原始的方向信息就丢了——
> 有些软件（比如某些相册）依赖这个标记判断"这张是竖拍的"，丢了就判断错。

### 5.3 拍照地点：6.4 万座城市塞进一个文件

照片的 EXIF 里可能带 GPS 坐标，比如 `北纬 30.2741, 东经 120.1551`。这串数字对人没意义，你想看的是"杭州市西湖区"。

**常规做法是调在线地图接口**（高德、百度）。这个项目**不这么做**，理由三条：

1. **隐私**：照片的拍摄地点是你最私密的信息之一。为了显示一个地名，把坐标发给第三方服务器，不值得。
2. **离线可用**：断网、在飞机上、在没有网的相机旁边，也得能用。
3. **免费且无限制**：在线接口有配额、有延迟、有服务挂掉的可能。

那怎么办？**内置一份城市表**：

- 数据来自 GeoNames（一个公开的地理数据库），取人口大于 5000 的城镇，**6.4 万条**；
- 预处理成紧凑的二进制格式，**1.9 MB**；
- 编译时直接**编进程序里**（`include_bytes!`），不是放在外面的文件——这样不会被误删、不会找不到路径。

运行时怎么查？给一个坐标，遍历 6.4 万条算距离，取最近的。听起来很笨，实际上一次也就几毫秒（而且可以先用粗略的矩形筛掉 99%）。

**这里有个很"产品"的细节**：取"最近的"不一定对。

比如你在澳门，最近的可能是珠海；在上海徐汇，最近的可能是郊区某个镇。用户看到"你在珠海"会觉得软件坏了。

所以规则是：**先按行政层级判断，同城范围内不取最近，取上级城市名**。这类规则没有算法能自动学到，是一遍遍试出来的。

> 还有一点属于合规要求：港澳台必须按规范命名（中国香港 / 中国台湾 / 中国澳门）。这不是技术问题，是必须做对的事。

### 5.4 AI 打标：把图片和文字放进同一个坐标系

"自动识别照片内容"听起来很玄。实际原理不复杂，值得讲清楚。

**核心思路：让模型学会"图和文字可以互相比较"。**

具体做法（这类模型叫 CLIP）：

1. 找一个"看图"的网络（视觉塔）和一个"看字"的网络（文本塔），一起训练；
2. 训练目标是：**一张猫的图片，跟"一只猫"这句话，在某个高维空间里应该离得很近；跟"一辆汽车"应该离得很远**；
3. 训练好之后，**图片和文字就都能变成一个 512 个数字组成的向量**（可以想成"512 个维度的坐标"）。

那么"给照片打标签"就变成了：

```
1. 预先准备好所有候选词："风景"、"人像"、"猫"、"汽车"、"美食"……（111 个词）
   每个词都算成一个向量，存下来（就是那个 448KB 的 text_embeds.bin）
2. 来一张新照片 → 算它的向量
3. 跟 111 个词的向量逐一算"相似度"（就是看两个箭头夹角有多小）
4. 相似度超过门槛的，就是这张照片的标签
```

**实测数据**：一张 1024 长边的图，模型加载 560 毫秒（只做一次），单张推理约 430 毫秒，输出 512 维向量。

几个工程上的讲究：

- **门槛是 0.39**（二级标签）/ **0.35**（一级类目）。这不是拍脑袋，是拿一批人工标过的图试出来的：阈值高了漏标，低了乱标；
- **一张图最多给 6 个标签**。多了就变成"什么都像"，用户反而看不出重点；
- **输入图要缩到 1024 长边再送进去**。试过 640，结果分数系统性偏低 0.01~0.02——因为缩小太狠，细节没了，模型"看不清"。这个 0.02 在 0.40 门槛附近就是整批漏标；
- **门槛只在配置里写一份**。曾经出现过"设置面板显示 0.40、实际跑的是 0.39"这种低级但致命的不一致，所以现在常量只有一处定义，其他地方都从它派生。

> **一个必须说清楚的点**：这套 AI 是**本地跑的**。模型文件（165MB）就在你电脑上，不联网、不上传照片。这也是为什么安装包有 200 多 MB。

### 5.5 人脸：为什么"一个阈值"聚不出人

自动把同一个人的照片归到一起，看起来是"算两张脸像不像"，其实难点在**怎么分组**。

每张脸经过模型，也变成一个向量。两张脸的向量越接近，越可能是同一个人。于是最简单的做法：**设一个门槛，像的就连起来**。

**这个做法会崩。** 原因很直观：

- 同一个人的照片，有正脸有侧脸，有笑有不笑，相似度可能在 0.45~0.95 之间波动；
- 不同的人，如果都是圆脸戴眼镜，相似度也可能到 0.55。

**两拨分数重叠了，一条线切不开。**

项目的解法是**分两步**（这是人脸聚类里很成熟的思路，叫"核心簇 + 归并"）：

```
第一步：用很高的门槛（0.55）先聚出"绝对是同一个人"的小簇
        —— 宁可漏，不可错。这些是"核心"

第二步：把剩下的散脸，逐个去跟每个核心簇的"代表脸"比
        超过稍低的门槛（0.50）就并进去
        —— 这一步宽松些，因为核心簇已经很干净，不容易误并
```

还有两条保底规则：

- **只有照片多的簇才建成"人物"**（至少 3 张脸）。1 张脸的簇大概率是误检，做成人物只会干扰你；
- **删人物时不能把其他图库的人物一起删掉**。技术上是个数据库外键问题，产品上是个"你删了我另一个图库的人就没了"的灾难。

## 6. 数据库：16 张表，为什么不"文件夹就是相册"

一个自然的想法是：**相册不就是文件夹吗？为什么还要数据库？**

因为你要做的是这些事：

- 一张照片**同时**属于"2024 杭州"、"猫"、"评分 5 星"、"人物：小王"——**四类关系同时成立**；
- 换台电脑，移动硬盘插到别的接口，**图库还得认得它**；
- 按"拍摄时间"排序，但有些照片没有拍摄时间，得退回用"入库时间"；
- 一张照片在一处，但要能在多个"智能图库"里出现（比如"所有 5 星照片"）。

**文件夹只能表达"一个东西在一个地方"。上面这些它一个都做不到。**

所以用 SQLite（一个单文件的数据库，整个库就是你硬盘上的一个文件，不需要装服务器）。

16 张表大致分五组：

| 组 | 表 | 存什么 |
|---|---|---|
| 位置 | `volumes` / `folders` | 磁盘卷、目录树 |
| 组织 | `libraries` / `library_folders` | 图库（用户建的"相册"）、图库包含哪些目录 |
| 照片 | `images` / `image_exif` / `places` / `image_places` | 每张照片一行、EXIF 明细、地点 |
| 语义 | `tags` / `image_tags` / `ai_results` / `persons` / `faces` | 标签、打标结果、人物、人脸 |
| 其他 | `thumbs` / `settings` / `vaults` | 缩略图记录、设置、加密图库 |

**几个设计决定值得说：**

**① 卷的身份用编号，不用盘符。**

```
volumes(id, guid, path)   ← guid 是这块盘的唯一编号
folders(id, volume_id, rel_path, ...)
images(id, folder_id, ...)
```

移动硬盘今天 `D:`、明天 `E:`，数据库里存的还是同一个 `volume_id`，照片不会"消失"。

⚠️ 但这里踩过一个很隐蔽的坑：**比较卷路径时必须先规范化**（去掉结尾的反斜杠、转小写）。差一个反斜杠，程序就认为"这是两块不同的盘"，于是同一批照片被索引两遍；更糟的是"移除目录"时删掉一份，另一份还在。

**② 删图库 ≠ 删照片。**

"删除图库"只删 `libraries` 和 `library_folders` 里的记录，**原图一张都不碰**。这是必须守住的红线：用户点"删除"的时候，心里想的是"不想在这个相册里看到"，不是"把这些文件从硬盘抹掉"。

**③ 默认排序是拍摄时间，但要有兜底。**

```sql
ORDER BY COALESCE(taken_at, added_ts)
```

有些照片（截图、从网上下载的、老相机）没有拍摄时间，就退回用入库时间。不用 `COALESCE` 的话，这些照片会全部沉到底部或者顶到最前。

## 7. 改照片：怎么做到"改坏了也不丢原图"

编辑照片意味着**重新写文件**。这里出错的后果很严重：写一半断电、磁盘满了、程序崩了——都可能得到一个"打不开"的文件，而原图已经没了。

### 7.1 原子写：先写新文件，再改名替换

```
1. 完整地在内存里编码好新图
2. 写到同目录下的临时文件（xxx.tmp）
3. 确认写完了 → 用一个"改名"操作把 tmp 换成原名
```

关键在**第 3 步**：在文件系统里，"改名"是一个**要么全成、要么全不成**的操作（原子操作）。所以任何时刻，硬盘上要么是完整的旧图、要么是完整的新图，**不存在"半个文件"**。

如果第 2 步就失败了（磁盘满），直接删掉 tmp，原图分毫未动。

### 7.2 EXIF 写回：一个能毁掉整份文件的陷阱

这个技术细节很硬核，但它是这个项目里"最值得讲"的 bug 之一。

EXIF 数据（拍摄时间、相机、方向）存在图片文件的一块区域里，结构像一张表格：每行有"标签、类型、数量、值"。

**陷阱在于"值"这一格。**

表格里这么设计是有原因的：大部分值很小（比如方向就是个 1~8 的数字），直接塞在"值"这一格里最省空间；但有些值很长（比如相机型号字符串、GPS 坐标数组），塞不进去，就在这一格里存一个**"到别处的偏移量"**（相当于"详情见第 300 字节"）。

**问题来了**：你怎么知道这一格是"值本身"还是"一个地址"？

规则是：**当"数量 × 类型长度 ≤ 4 字节"时是值本身，否则是偏移量。**

于是有了这样一个 bug：

> 早期代码写方向标记时，默认"这一格一定是 2 字节的小数字，直接改"，就把值写了进去。
> 但如果这个文件里那一格存的其实是个**偏移量**（因为别的软件写入时用了更宽的格式），
> 那么"直接改数字"等于**把指针改坏了**——读图软件顺着这个假地址去读，读到一堆垃圾，
> 结果整个文件的 EXIF 全部解析失败，严重时文件打不开。

修复后的逻辑是**先辨类型和数量，再决定怎么写**：

```rust
fn orientation_slot(e: &Entry, tiff: &[u8]) -> Option<(usize, Width)> {
    if e.count != 1 { return None; }          // 数量不是 1 → 不是内联值，别碰
    let width = match e.ty {
        TYPE_SHORT => Width::Short,           // 2 字节
        TYPE_LONG  => Width::Long,            // 4 字节
        _ => return None,                     // 其他类型 → 别碰
    };
    let at = e.offset.checked_add(8)?;        // 内联值的位置
    tiff.get(at..at.checked_add(width.bytes())?)?;  // 越界就放弃
    Some((at, width))
}
```

**看不懂代码没关系，记住这个思路就行**：不确定的地方，**宁可放弃，也不要猜着写**。返回 `None` 的后果只是"这次没改成功"，而猜错的后果是"用户的原图废了"。这个取舍在生产代码里是标准答案。

## 8. 工程纪律：这部分其实比算法更值钱

前面讲的都是"做了什么"。这一节讲"怎么保证做得对"——**这部分是外行最难体会、但内行最看重的**。

### 8.1 一次只改一件事，改完立刻验证

这个项目有条硬规矩：**每一刀只搬代码、不改逻辑**，然后跑三项检查（类型检查、单元测试、代码规范检查），全绿才提交。

为什么要这么死板？因为**如果一次改三件事，出了问题你根本不知道是哪一件引起的**。

举个真实的例子：把图库视图里"拖拽调宽"这段搬出去的时候，顺手发现了一个真 bug——

> 双击侧栏那条缝，界面上的宽度确实回到默认了，但这个值**没有存下来**。
> 重启软件，宽度又变成上次拖的那个值。
> 界面上写着"双击恢复默认"，行为却是"暂时恢复默认"。

这个 bug 存在了很久，但没人发现。**为什么搬代码的时候会突然发现？**

因为在原来那一堆内联的事件处理里，你只能看到"改了内存里的值"；搬出来单独看的时候，"改内存"和"写磁盘"这两件事摆在一起，缺了哪个一目了然。

> 这就是重构（把代码重新摆放）的真正价值：**它不是为了好看，是为了让错误无处藏身。**

### 8.2 测试不是"证明对"，是"防止退步"

项目里现在有 **343 个前端测试 + 532 个后端测试**。

这些测试绝大多数不测"高深的算法"，而测**很容易被后人改坏的小规则**。举几个真实的例子：

```
"全选文件夹时，不能显示大小"
  → 因为目录没有 size，算出来是 0，会显示"已选 3 张 · 0 B"，
    既把文件夹说成"张"，又摆了个假的大小

"取路径的函数故意不过滤目录"
  → 因为侧栏"加入图库"正是靠它取目录路径的，
    谁要是"顺手优化"加上"排除目录"，这个功能立刻坏掉

"0.55 和 0.50 是两个不同的门槛，别合成一个"
  → 人脸聚类分两步的原因就写在这个测试的注释里
```

**关键在注释。** 每条测试都写清楚"为什么是这个行为"，以及"⛔ 别改成什么样"。因为半年后回来看代码的人（可能就是自己）只会看到一行奇怪的断言，然后想"这明显是多余的，删了吧"。

### 8.3 把踩过的坑写下来，而不是记住

项目里有一份"记忆索引"，全是这种条目：

```
⛔ 读缓存不能传 new(Thumbnail)，要用 exact(Thumbnail, None)
⛔ 弹层必须挂在 body 上，塞进 overflow:hidden 的容器里会看不见
⛔ hook 必须写在所有提前 return 之前，否则整页白屏
⛔ 后端别按总行数拆：lib.rs 1348 行里 1104 行是测试
```

这些每一条背后都是一次真实的排查。写下来的原因很简单：**人会忘，文件不会。**

## 10. 名词小抄

| 名词 | 一句话解释 |
|---|---|
| **Rust** | 一门编程语言，跑得快、不容易崩，编译时检查特别严 |
| **React** | 做界面的工具库，"数据一变界面自动变" |
| **Tauri** | 把网页打包成桌面程序的框架，比 Electron 小得多（因为它用系统自带的浏览器内核） |
| **crate** | Rust 的"包/车间"，一个独立编译的代码单元 |
| **IPC / 命令** | 界面和后端说话的通道；一次请求就是一条"命令" |
| **SQLite** | 一个文件就是一个数据库，不用装服务器 |
| **EXIF** | 照片里附带的"说明书"：拍摄时间、相机、光圈、GPS、方向 |
| **RAW** | 相机原始数据格式，没经过压缩处理，画质最好但文件巨大 |
| **解码** | 把压缩的图片文件变成屏幕上能显示的像素 |
| **编码** | 反过来，把像素存成 jpg/png 文件 |
| **降采样** | 把大图缩小（缩略图的关键步骤） |
| **缓存** | 把算过的东西存起来，下次直接用 |
| **哈希** | 把任意内容算成一串固定长度的"指纹"，内容变一点指纹就全变 |
| **向量 / 相似度** | 把事物变成一串数字，两个向量的夹角越小越相似 |
| **CLIP** | 一类能把"图"和"文字"放进同一个坐标系的 AI 模型 |
| **阈值 / 门槛** | 判断"算不算"的那条线，比如相似度 0.39 以上算是这个标签 |
| **聚类** | 把相似的东西自动分成一堆一堆 |
| **原子操作** | 要么全做完、要么完全没做，不存在"做了一半" |
| **单元测试** | 一段小程序，自动检查某个功能还是不是预期的样子 |
| **重构** | 不改功能，只重新摆放代码，让它更好懂、更好改 |

## 最后

如果只能记住三件事：

1. **分层是为了各司其职**——界面负责"快响应"，后端负责"算得快又不崩"，中间那条通道让责任边界很清晰。
2. **性能的关键往往在"少干活"**，而不是"干得快"。缩略图不解整张、缓存按指纹命中、地名不联网——都是"少干"。
3. **工程上最值钱的不是聪明，是纪律**：一次只改一件事、每件事都有测试守着、每个坑都写下来。

一个 6 万行的软件，本质上是**几百个这样的决定堆起来的**。每个决定单看都不难，难的是让它们互相不打架，并且在半年后还能被改。
