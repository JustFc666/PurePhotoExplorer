### 🔑 最重要的一个结论

> **原规划里「S3 是唯一被 MSVC 阻断的阶段」这个前提，已经不成立了。**
>
> 实际走通了**两条纯 Rust 路线**，把 MSVC 从关键路径上彻底摘掉了：
> - **HEIC**：`heif-oxide`（纯 Rust 容器解析 + `rust_h265` 软解 HEVC），无 C、无 unsafe

## 1. 为什么重排（历史决策，保留）

原 §10 的 M0→M8 是"功能导向"排序，按 R1→R6 需求顺序推进。
重排为"依赖度导向"，理由：

| 问题 | 原排序 | 重排后 |
|---|---|---|
| MSVC 阻断 | M0 就要面对 LibRaw 编译，可能整条路线被卡 | S1/S2 完全用纯 Rust，**不碰 MSVC** |
| 首次可见成果 | M0 结束时只有一个 demo | S1 结束就是**能用的单图浏览器** |
| 风险暴露 | 格式解码风险到 M2 才验证 | S1 已用 e2e 测试验证解码链路 |
| 返工成本 | 前端/渲染在 M3 才定型 | S1 定型的接口后续不变 |

**核心判断：单图浏览是整个项目的最小完整闭环**——它一次性打通
格式探测 → 解码 → 缓存 → IPC → 渲染，验证了全链路。
而资源管理器、编辑、加密、AI 都只是在这条链路上"加数据源"或"加后处理"。

**这个判断已被证实**：S1 定下的 `ImageDecoder` / `DecodeTarget` / `RawPipeline` 接口，
后续接 HEIC、PSD、GIF、WebP、RAW **一行架构都没改**，只是往 `BitmapBackend` 里加解码器。

#### S1 交付物实测

| 指标 | 实测 |
|---|---|
| 像素 IPC | **裸字节 `tauri::ipc::Response`**，不走 JSON/base64 |
| 动图 | 299 帧 × 250×250 = 71.3MB，**首批 167ms 就开播**，余量后台补齐 |
| RAW 预览 | 4032×3024（DNG 等 8 种机型实测） |
| 交互 | 滚轮锚点缩放 / 翻页 / 旋转 / 裁剪 / 快捷键 |

#### S1 关键技术决策（踩坑后定下的）

1. **像素数据不走 JSON**。6000×4000 的 RGBA 是 96 MB，序列化成 JSON 会膨胀到 200 MB。
   自定义 `PVI1`/`PVA1` 包头 + 原始 RGBA。
   ⚠️ **前提是 CSP 必须放行 `connect-src ipc: http://ipc.localhost`** —— 漏配会让所有 IPC
   永久回退到 `window.ipc.postMessage`，那条通道对大响应要走 `webview.eval()`（拼 JS 源码），
   几十 MB 要好几秒。已加测试断言守着。
2. **`ImageDecoder: Send + Sync`**。Tauri 命令在多线程运行时执行。
   **S8 接 LibRaw 时必须用 `Mutex` 包装**，约束已写进 trait 文档注释。
3. **用 `<canvas>` + `putImageData`**，不用 `<img>`，也不要用
   `createImageBitmap(ImageData)`（WebView2 坑）。
4. **`Response` 不包 `Ok`**。`tauri::ipc::Response` 自己实现了 `IpcResponse`，再包一层会类型不匹配。
5. **格式判定只看魔数，不信扩展名** —— e2e 测试抓到过「扩展名是 .jpg 的 PNG 文件」被解码失败。

| 项 | 内容 | 规划路线 | 实际 |

| S3.5 | RAW 覆盖率设置页 | — | ❌ 但**格式能力表已存在**（`supported_formats`，驱动打开对话框与帮助面板） |

#### 路线变更的原因（实测得出，不是推测）

- **Windows WIC 走不通**：`CreateDecoderFromFilename` 成功但 `GetFrame(0)` 返
  `0x88982F44`（`WINCODEC_ERR_FRAMEMISSING`），因为没装 `Microsoft.HEVCVideoExtension`。
  任何"用系统解码器"的路都要求用户先装扩展，**不能自包含**。
- **libheif/libde265 要 cmake + nasm**，本机没有，且引入 C 依赖违背 S1 起的"纯 Rust"原则。
- **样本里没有内嵌缩略图可降级**：53 个 `hvc1` + 1 个 `grid`，**全文件无 JPEG/PNG**，
  所以"读内嵌缩略图"这条常见的省事路在 HEIC 上也不存在。

**注意**：HEIC 的 `probe_heif` **是全解码**（库未暴露轻量容器查询），98ms 可接受。
自己手写 `ispe`/`grid`/`ipma` 猜尺寸反而会导致「信息面板写 4032×3024、实际 3024×4032」。

## 6. 两条必须记住的教训

### 教训 1：接口定死比功能先行更重要

S0 阶段看似"没做功能"，只定义了 trait 和数据结构。
但正是这一步让后续接 HEIC / PSD / GIF / WebP / RAW **都不需要改 S1 一行架构**。

**反面教材**：如果 S1 直接在业务代码里写 `image::load_from_file()`，
后面每接一种格式都要改遍所有调用点。

### 教训 2：静默失败比崩溃更危险

e2e 测试抓到过一个真实缺陷：**`BitmapBackend` 内部按扩展名分发解码器**，
而注册表按 magic bytes 路由 → 「扩展名是 .jpg 的 PNG 文件，注册表认对了但后端解码失败」。
这个 bug 在纯逻辑单测里完全不会暴露，**是端到端的真实像素校验抓住了它**。

同理，**S6 的容器缩略图明文落盘也是静默失败**：加密看起来正常工作，
但安全上已完全失效。所以 S6 必须有独立的"全盘扫描无明文"集成测试。

> **原则：任何安全/正确性约束，都必须有独立测试覆盖，不能指望功能测试顺带发现。**

### 教训 3（2026-10-10 新增）：修 bug 要先验证原因本身

修「坏图上滚轮翻不过去」时，我先按推断改了代码（滚轮监听挂在画布上、
错误页把画布卸载了）—— 代码上确实成立，**改完一测还是翻不动**。
加诊断日志后才看清真相是 `folder.rs::IMAGE_EXTS` 白名单缺 `psd`，
导致列表只有 2 项、滚到第 2 项就已经是"最后一张"。

## 7. 下一步建议

**按性价比排序**（不是按原规划顺序）：

1. **S2 资源管理器** —— 当前唯一瓶颈，且所有下游都依赖它。
   现成资产：EXIF 解析、缓存键、缩略图层级、同目录翻页。
   ⚠️ 别忘了 `pv-cache` 现在是**空文件**，L1/L2 缓存要从头写。
2. **S4.1 + S4.3 线性域与调色** —— 调色是 S4 的主体工作量（6 项里占 5 项），
   且做完后 S5 导出才有意义。⚠️ 注意「覆盖原图」已取代 XMP sidecar，
   多步编辑的可撤销性需要重新设计。
3. **S6 加密** —— **可以现在并行开工**，与 S2 无依赖、不需要 MSVC。
4. **S3 收尾**（0.5 周）—— AVIF 支持、无内嵌预览机型的降级路径。

**已可交付**：当前 exe 已是可日常使用的看图工具（6 种格式 + RAW 预览 + 动图 + 打印 + 文件关联）。
